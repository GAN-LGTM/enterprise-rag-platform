## 二、上线前检查表

### 2.1 安全基线（任一未过 = 不得上线）

- [ ] 已执行 `python deploy/init_env.py` 生成 `.env.production`，**所有默认口令已替换**
- [ ] `JWT_SECRET_KEY` 为强随机值（≥32 字符），未使用仓库示例值
      （生产环境若为默认值，preflight 门禁会直接拒绝启动）
- [ ] `PG_PASSWORD`、`REDIS_PASSWORD` 非弱口令，且未提交进版本库
      （Redis 生产已强制 `requirepass`，compose 无法以空口令启动）
- [ ] `backend/data/initial_admin.txt`（含初始 admin 明文口令）**已删除或已改密**
- [ ] `ALLOWED_ORIGINS` 已配置为实际域名，**不是 `*`**
- [ ] TLS 证书已挂载（`server.crt` / `server.key`），且未使用自签证书对外服务
- [ ] 交付镜像内**不含**运行时凭据：`.dockerignore` 已排除 `backend/data`
      （含 `initial_admin.txt` 明文口令、审计与令牌文件）、`.env*`、`logs/`、`backups/`
      —— CI 的「交付卫生」job 会强制校验该清单，防止被误删
- [ ] 会话令牌安全：业务接口只接受 `typ=access` 的令牌（`refresh_token` 不能当访问令牌用），
      登出后访问令牌立即失效；多 worker 部署下黑名单状态跨进程可见
- [ ] 演示账号接口已随 `DEMO_MODE=false` 关闭（`GET /api/auth/demo-accounts` 返回 404）
- [ ] `OFFLINE_MODE` 与 `PUBLIC_SEARCH_ENABLED` 按甲方合规要求设定
      （金融 / 政务零外网场景：总开关保持关闭）
- [ ] 已确认行级安全（RLS）的启用状态：**默认未启用**，权限隔离由应用层
      `backend/app/perm/policy.py` 的检索前硬拦截保证。若甲方要求"数据库层二次兜底"，
      按 `sql/003_rls.sql` 顶部说明完成两步接线（应用改以非 superuser 角色连接 +
      每次查询 `SET LOCAL app.current_depts`），**未完成这两步时 RLS 不会拦截任何查询**

### 2.2 备份与恢复（**必须做过一次真实恢复演练**）

- [ ] `BACKUP_DIR` 指向独立卷，**不在容器可写层**（compose 已配 `backupdata`）
- [ ] 执行过一次 `python backend/scripts/backup.py backup` 且成功
- [ ] 执行过一次 `python backend/scripts/backup.py verify` 且返回可解析
- [ ] **在演练环境执行过一次完整 `restore` 并验证业务可用** —— 能备份 ≠ 能恢复
- [ ] 已配置定时备份（crontab 每天全量）+ 备份失败告警
- [ ] `BACKUP_KEEP` 保留策略与甲方留存要求一致（默认 14 份）

### 2.3 监控与告警

- [ ] Prometheus 已加载 `deploy/monitoring/alerts.yml`，`/alerts` 页面可见 12 条规则
- [ ] Alertmanager 已配置通知渠道（企业微信 / 钉钉 / 邮件），**并做过一次告警触达测试**
- [ ] `critical` 级告警有明确的响应人与响应时限
- [ ] 备份失败有独立告警（备份是独立进程，不进 Prometheus，靠 cron 日志或退出码）

### 2.4 容量与性能

- [ ] `WEB_CONCURRENCY` 按 CPU 核数调整（默认 2）
- [ ] PostgreSQL `max_connections` ≥ 连接池上限（默认 20 + 10 overflow）
- [ ] Redis `maxmemory` 已设定且有淘汰策略（compose 默认 2gb + allkeys-lru）
- [ ] 文档上传体积限制前后端一致（Nginx `client_max_body_size 50m` ↔ 后端 `MAX_UPLOAD_MB=50`）
- [ ] 已做一次并发压测，P95 延迟在可接受范围（告警阈值设为 8s）

### 2.5 数据与业务

- [ ] 知识库已完成初始导入，检索召回效果经业务方确认
- [ ] 部门与角色授权已按甲方组织架构配置，权限拦截经抽样验证
- [ ] 演示数据（`DEMO_MODE`）在生产已关闭
- [ ] 审计日志可查询且保留周期满足合规要求

## 三、回滚预案

原则：**任何一步都要能退回去，且退回后业务仍可用**。回滚前先记录当前版本号与备份名。

### 3.1 应用回滚（代码/镜像问题，最常见）

```bash
# 1. 记录当前版本
docker inspect rag-api --format '{{.Config.Image}}' | tee /tmp/current_image.txt

# 2. 改回上一个版本的镜像 tag 并重建（数据库不动，风险最低）
APP_VERSION=<上一个版本> docker compose --env-file .env.production -f deploy/docker-compose.prod.yml up -d api

# 3. 验证
curl -fsS http://<host>/api/health
```

> 只回滚应用不回滚数据库：**前提是本次上线没有改表结构**。
> 若改过表结构，必须先按 3.2 回滚数据库，否则旧代码读新表会报错。

### 3.2 数据库回滚（数据出问题）

```bash
# 1. 先看清有哪些备份可用
python backend/scripts/backup.py list

# 2. 恢复到指定备份（会自动先对当前库做安全备份，返回的 revert_to 可用于反悔）
python backend/scripts/backup.py restore backup-20260929-020000

# 3. 验证数据行数与关键表
# 4. 若恢复错了，用第 2 步返回的 revert_to 再恢复一次即可
```

恢复后必须同步回滚应用到**与该备份同时代**的版本，避免代码与数据结构不匹配。

### 3.3 前端回滚

前端是静态文件（Nginx 直接挂载），回滚只需替换 `frontend/` 目录内容：

```bash
# 保留一份当前版本再覆盖
mv frontend frontend.bak.$(date +%Y%m%d-%H%M%S)
cp -r <上一版本frontend> frontend
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml restart web
```

### 3.4 回滚后的必做验证

- [ ] `/api/health` 返回 healthy，版本号与预期一致
- [ ] 用业务账号登录并发起一次问答，确认能正常返回且有引用
- [ ] 抽查一次无权限问题，确认仍被正确拦截（回滚不能把安全边界一起回退）
- [ ] 查看审计日志，确认回滚操作本身已被记录
- [ ] 在变更记录中补充回滚说明与根因
