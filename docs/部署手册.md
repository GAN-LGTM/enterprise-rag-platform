# 部署手册（私有化交付版）

> 适用：甲方内网 / 专有云环境，全程离线运行，启动后零外网流量。
> 目标读者：实施工程师。按本手册顺序执行即可完成一套可交付环境。

---

## 0. 交付清单核对

交付物目录（建议随代码一并移交）：

| 类别 | 路径 | 说明 |
| --- | --- | --- |
| 后端服务 | `backend/` | FastAPI + LangGraph + SSE |
| 前端页面 | `frontend/index.html` + `app.js` + `styles.css` + `antd-bridge.js` + `vendor/` | 免构建静态资源，直接由 Nginx 托管 |
| 数据库脚本 | `sql/001_schema.sql`、`002_index.sql`、`003_rls.sql` | 建表 / 索引 / 行级安全 |
| 生产镜像 | `deploy/Dockerfile` | 多阶段构建、非 root 运行 |
| 编排文件 | `deploy/docker-compose.prod.yml` | PostgreSQL + Redis + API + Nginx |
| 反向代理 | `deploy/nginx.conf`、`deploy/api_proxy.inc` | TLS、限流、SSE 关闭缓冲 |
| 配置模板 | `.env.production.example` | 由 `deploy/init_env.py` 生成实际配置 |
| 依赖锁定 | `requirements.lock.txt` | 全量锁定版本，用于离线/内网 `pip install -r requirements.lock.txt`；容器构建装 `requirements.txt`，CI 会校验锁定文件覆盖全部直接依赖 |
| 初始化脚本 | `deploy/init_env.py` | 生成密钥与管理员口令 |
| 备份脚本 | `backend/scripts/backup.py` | 数据库 + 文件备份与清理 |
| 一键回归 | `backend/scripts/run_all_tests.py` | 串行执行全部测试套件并汇总，`RUN_E2E=1` 追加端到端 |
| 验收文档 | `docs/验收测试.md` | 37 项验收用例 + 自动化回归说明 |

## 1. 环境要求

| 组件 | 版本 | 备注 |
| --- | --- | --- |
| 操作系统 | Linux（CentOS 7.9+ / Ubuntu 20.04+） | Windows 仅用于开发调试 |
| Docker | 24.0+，含 Compose V2 | `docker compose version` 验证 |

## 2. 部署步骤

### 2.1 准备目录与介质

```bash
mkdir -p /opt/rag/{data,models,backup,certs}
# 解压交付包到 /opt/rag，模型权重拷入 /opt/rag/models
```

### 2.2 生成生产配置

```bash
cd /opt/rag
python deploy/init_env.py --origins https://rag.客户域名.com
```

脚本会生成 `.env.production`（权限 600），包含：

- `JWT_SECRET_KEY`：随机 64 位密钥
- `ADMIN_INITIAL_PASSWORD`：初始管理员口令（**首次登录强制改密**）
- `PG_PASSWORD`：数据库口令

> 生产环境**关闭演示模式**（`DEMO_MODE=false`）：不预置任何演示账号、不灌入示例语料。

### 2.3 配置模型与 LLM

编辑 `.env.production`：

- 有 GPU：`LLM_BACKEND=vllm`，启用 `--profile gpu`
- 无 GPU：指向客户已有的 OpenAI 兼容推理服务（`LLM_BASE_URL`），或改用云端（需 `ALLOW_CLOUD_LLM=true`）
- 向量：`EMBEDDING_BACKEND=local` + `EMBEDDING_MODEL_PATH=/data/models/bge-large-zh-v1.5`

### 2.4 准备 TLS 证书

将 `server.crt` / `server.key` 放入 `deploy/certs/`（或用 `TLS_CERT_DIR` 指定）。
内网 HTTP 直连场景可删除 `nginx.conf` 的 80 跳转段并把 443 段改为 80。

### 2.5 启动

```bash
# 在项目根目录执行；--env-file 不可省略：
#   compose 的 ${VAR} 插值只读 shell 环境与 compose 文件同级的 .env，
#   不会读 service 的 env_file。缺了它，PG_PASSWORD / REDIS_PASSWORD
#   取不到值，compose 会在解析阶段直接报错。
# 无 GPU
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml up -d

# 含 GPU（本地大模型推理）
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml --profile gpu up -d
```

首次启动会自动执行 `sql/` 下的建表脚本（PostgreSQL 初始化目录）。

### 2.6 验证

```bash
curl https://rag.客户域名.com/api/health
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml logs -f api

# 交付自检：在应用主机上跑一遍回归（无需外部服务依赖）
cd backend && python scripts/run_all_tests.py
```

启动自检会在日志中打印检查结果；**生产环境任一安全基线不合规会直接拒绝启动**，
并在日志中给出检查项名（致命项抛错格式 `[<检查项名>] <原因>`，非致命项日志事件名 `preflight.<检查项名>`），例如：

| 检查项 | 拒绝原因 |
| --- | --- |
| `jwt_secret` | 仍为默认密钥或长度 < 32 |
| `demo_mode` | 生产环境开启了演示模式 |
| `embedding_backend` | 使用伪向量 `hash`（检索结果不可信） |
| `database` | `DB_FORCE_MEMORY=true`（内存库重启即丢） |
| `llm_backend` | `mock` 或私有化下外联云端 LLM |
| `cors` | `ALLOWED_ORIGINS=*` |

## 3. 初始账号与权限

1. 首次启动后，用 `.env.production` 中的 `ADMIN_INITIAL_USERNAME` / `ADMIN_INITIAL_PASSWORD` 登录；
   未配置口令时，系统会在 `data/initial_admin.txt`（权限 600）生成随机口令。
2. 登录后系统会**强制修改初始密码**，改密完成后请删除 `initial_admin.txt`。
3. 业务账号通过下列方式接入：
   - **管理员建号**（已实现）：管理看板 →「用户管理」新增账号，或 `POST /api/admin/users`；
   - **按数据模型导入**（已实现）：按 `backend/app/db/models.py` 中的 `User` 结构导入（含 `dept_id`、`role`）；
   - **LDAP / SSO 单点登录**（**需二次开发**）：本仓库未内置身份源对接。若甲方要求 AD/LDAP/OIDC
     登录，需按企业身份中台实现登录接口并把身份属性映射到 `User`（`role` / `dept_id` / `managed_dept_ids`），
     现有 `api/auth.py` 的账号密码登录可保留为本地兜底。

角色与数据范围：

| role | 可见范围 | 上传文档 | 删除文档 |
| --- | --- | --- | --- |
| admin | 全部部门 | ✅ | ✅ 直接删除 |
| executive | 管辖事业部 | ✅ | 需管理员审批 |
| dept_director | 本事业部 | ✅ | 需管理员审批 |
| sub_manager | 本部门 | ✅ | 需管理员审批 |
| sub_employee | 本部门 | ❌ | ❌ |
| knowledge_reviewer | 知识治理范围（知识审核员） | ✅ | 需管理员审批 |
| compliance_reviewer | 全部部门（只读审计视角） | ❌ | ❌ |

共 7 种角色（对应 `backend/app/core/user_admin_store.py` 的 `VALID_ROLES`），
建号时的角色下拉即取自该表，避免手填字符串出错。

## 4. 数据与安全基线

- 数据库：PostgreSQL + pgvector；权限隔离由应用层「检索前硬拦截」保证
  （`backend/app/perm/policy.py`）。`sql/003_rls.sql` 提供数据库层兜底策略，
  **但默认不生效**（应用以库 owner 连接，PostgreSQL 会绕过 RLS），
  需要二次开发完成接线，详见该脚本顶部说明
- 传输：全站 HTTPS（TLS 1.2+），登录接口独立限流 1r/s
- 存储：口令 bcrypt 哈希；JWT 签名密钥由部署脚本随机生成
- 审计：登录、检索、上传、删除、审批全量留痕（`audit`），支持按用户/类型查询
- 备份：`python backend/scripts/backup.py backup`（含 PostgreSQL 全量；失败会非 0 退出）
- 恢复：`python backend/scripts/backup.py restore <备份名>`（恢复前自动安全备份，可反悔）

## 5. 升级与回滚

```bash
# 升级（先备份，备份失败则不要继续）
python backend/scripts/backup.py backup || exit 1
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml pull
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml up -d

# 回滚：改回上一个版本的镜像 tag（数据库未变更时最低风险）
APP_VERSION=<上一个版本> docker compose --env-file .env.production -f deploy/docker-compose.prod.yml up -d api
# 若需回滚数据库：python backend/scripts/backup.py restore <备份名>
# 详细回滚步骤与验证清单见 docs/交付检查清单.md

# 回滚：切回上一版本镜像标签后重启
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml down
docker compose --env-file .env.production -f deploy/docker-compose.prod.yml up -d
```

数据库结构变更请按 `sql/` 中脚本顺序执行，并在维护窗口内完成。

## 6. 常见故障

| 现象 | 排查 |
| --- | --- |
| API 启动即退出 | 查看 `docker logs rag-api`，按日志中的 `[<检查项名>] <原因>` 修正配置 |
| 检索结果为空 | 确认文档已入库（`/api/knowledge/docs`），向量模型路径正确 |
| SSE 不流式 | 确认经过 Nginx 且 `proxy_buffering off`（见 `api_proxy.inc`） |
| 上传失败 | 检查 `MAX_UPLOAD_MB` 与 Nginx `client_max_body_size` 是否一致 |
| 回答很慢 | 检查 Redis 是否启用、LLM 首字超时（3s）与降级是否触发 |
